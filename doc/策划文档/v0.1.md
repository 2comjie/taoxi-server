# 田园经营游戏 V0.1 系统策划案

> 文档版本：0.1.0  
> 产品阶段：第 1/10 个迭代版本  
> 客户端：Unity  
> 服务端：Go  
> 文档用途：作为 V0.1 的策划、客户端、服务端和测试共同实施基线

---

## 0. 文档结论

V0.1 的目标不是做出一款内容完整的游戏，而是完成并验证最核心的经营闭环：

```text
登录 → 种植 → 收获 → 加工 → 提交订单
     → 获得金币和经验 → 升级 → 解锁新内容 → 继续经营
```

本版本必须有 Go 服务端存档，所有资源结算由服务端完成。Unity 负责输入、表现、倒计时显示和界面流程。

本版本共实现 13 个系统：

1. 启动与账号
2. 玩家档案与存档
3. 配置与版本
4. 服务器时间与离线结算
5. 物品、货币与背包
6. 农田种植
7. 固定建造点与生产建筑
8. 加工生产
9. 订单
10. 等级、经验与解锁
11. 任务与新手引导
12. 主场景、交互与基础 UI
13. 邮件、日志与运营基础

本版本明确不实现：自由家园编辑、NPC 好感、剧情分支、探索、好友、拜访、大厅、组队、乡社、交易、活动、支付、排行榜和正式商业化。

## 2. V0.1 版本目标

### 2.1 产品目标

- 玩家第一次进入后，10 分钟内理解种植、加工和订单关系。
- 玩家能连续游玩 30～60 分钟，不因资源断链永久卡死。
- 玩家关闭游戏数小时后再次进入，作物和生产队列能够正确结算。
- 玩家达到 10 级后，能够体验全部首版生产内容。
- 策划可以只修改配置表，就调整作物、配方、订单和等级节奏。
- 客户端重装或更换设备后，登录同一账号可以恢复进度。

### 2.2 技术目标

- 任何金币和物品变化均由 Go 服务端执行。
- 所有写操作支持幂等，重复请求不能重复发奖或重复扣除。
- 客户端本地时间不参与成熟、生产完成和每日刷新判定。
- 配置具有版本号，客户端和服务端可以检查配置兼容性。
- 所有核心资源变化有可查询流水。
- 服务端进程重启后，玩家状态可以从数据库恢复。

### 2.3 版本验收指标

| 指标 | 验收要求 |
|---|---|
| 首次核心闭环 | 新玩家 10 分钟内完成至少一次“种植—加工—订单” |
| 主流程阻断 | 无必现阻断问题 |
| 资源正确性 | 重连、重复点击、弱网下不得复制或丢失资源 |
| 存档恢复 | 账号重新登录后核心数据一致 |
| 配置能力 | 修改作物时长和订单奖励不需要修改客户端代码 |
| 首版内容 | 6 作物、3 生产建筑、9 配方、4 订单槽、10 等级、15 引导任务 |
| 单次请求 | 正常网络下核心操作服务端处理目标小于 200ms，不含网络耗时 |
| 崩溃和异常 | 无高频崩溃；关键请求失败有明确提示和恢复方式 |

## 6. 全局技术与策划规则

### 6.1 服务端权威

以下结果必须由服务端计算：

- 是否拥有足够金币和材料
- 是否满足解锁条件
- 作物是否成熟
- 生产是否完成
- 背包是否有足够空间
- 订单能否提交
- 经验是否升级
- 任务是否完成
- 奖励内容和实际发放结果

客户端可以预测展示，但不得以客户端结果作为最终结算依据。

### 6.2 时间规则

- 全部时间存 Unix 毫秒时间戳。
- 服务端内部统一使用 UTC。
- 客户端通过 `serverTime` 计算显示倒计时。
- 客户端每次收到服务端响应都可以修正时间差。
- V0.1 每日刷新时间暂定为服务器当地时区 05:00。
- 农田和生产不依赖定时器主动扫描；玩家查询或操作时根据结束时间惰性计算。

### 6.3 幂等规则

每个资源写请求必须携带 `requestId`：

```text
requestId = 设备会话标识 + 本地递增序号 + 随机串
```

服务端保存近期已完成请求结果。相同玩家重复提交相同 `requestId` 时，直接返回第一次的结果。

重点保护请求：

- 收获作物
- 开始生产
- 领取产品
- 提交订单
- 领取任务奖励
- 领取邮件
- 领取升级奖励

### 6.4 事务规则

一个业务操作中的扣除、增加和状态改变必须在同一数据库事务中完成。例如订单交付：

```text
校验订单
→ 扣除订单物品
→ 增加金币和经验
→ 更新订单状态
→ 生成新订单
→ 写资源流水
→ 提交事务
```

任一步失败则全部回滚。

### 6.5 通用状态版本

玩家核心数据维护递增的 `revision`。写操作成功后版本号增加。响应返回新版本号，客户端发现版本跳跃或冲突时重新拉取玩家快照。

## 7. SYS-01 启动与账号系统

### 7.1 系统目标

完成客户端启动、版本检查、账号身份建立、会话恢复和进入游戏。

### 7.2 V0.1 登录方式

首选两种：

1. 游客登录：设备首次运行生成 `guestToken`。
2. 开发账号：开发环境输入账号名直接登录。

正式渠道、手机号和第三方登录放到后续版本，但玩家 ID 从首版开始采用全局唯一 ID。

### 7.3 启动状态机

```text
Boot
→ CheckLocalAssets
→ CheckVersion
→ LoadConfig
→ Login
→ LoadPlayerSnapshot
→ EnterHome
```

失败状态统一进入：

```text
RecoverableError → 重试/重新登录
MandatoryUpdate → 跳转更新
Maintenance → 展示维护公告
FatalError → 上报错误并返回登录页
```

### 7.4 玩家初始数据

新玩家创建时获得：

- 铜钱：500
- 玉石：0
- 玩家等级：1
- 当前经验：0
- 背包容量：100
- 已开放农田：1～4 号
- 已解锁作物：小麦
- 已解锁建筑：磨坊建造点
- 小麦种植权限
- 任务：T001
- 订单系统：未解锁，按任务开启

### 7.5 主要接口

| 接口 | 用途 |
|---|---|
| `POST /auth/guest` | 游客登录或恢复游客账号 |
| `POST /auth/dev-login` | 开发环境账号登录 |
| `POST /auth/refresh` | 刷新会话令牌 |
| `GET /game/bootstrap` | 获取服务器时间、配置版本和玩家快照 |
| `POST /game/logout` | 主动退出并结束会话 |

### 7.6 异常规则

- Token 过期：自动刷新一次，失败后返回登录页。
- 重复登录：V0.1 采用新会话顶掉旧会话。
- Bootstrap 超时：保留登录态，允许重新请求。
- 新角色创建中断：使用唯一玩家 ID 和事务保证不会创建两份初始资产。

### 7.7 验收标准

- 首次启动可以生成唯一账号并进入家园。
- 重启客户端后自动恢复账号。
- 同一账号重新登录，金币、农田、生产、订单和任务完全一致。
- 登录接口重复请求不会重复发放初始资源。

## 8. SYS-02 玩家档案与存档系统

### 8.1 玩家档案字段

```text
PlayerProfile
- playerId
- displayName
- avatarId
- level
- exp
- createTime
- lastLoginTime
- lastLogoutTime
- tutorialStep
- revision
```

V0.1 昵称默认生成“山民 + 6 位数字”，头像固定，可在开发界面修改。

### 8.2 存档原则

- 服务端数据库是唯一正式存档。
- 客户端只保存登录凭证、配置缓存和显示设置。
- 客户端不保存可直接恢复的完整资源存档。
- 每个业务系统独立持久化，Bootstrap 聚合为玩家快照。

### 8.3 玩家快照内容

```text
BootstrapResponse
- serverTime
- configVersion
- playerProfile
- currencies
- inventory
- farmPlots
- buildings
- productionQueues
- orders
- quests
- unlocks
- mailsSummary
- revision
```

### 8.4 验收标准

- 玩家在任意核心操作后强退，重新登录数据正确。
- 服务端重启后存档不丢失。
- 快照中的资源总数与资源流水最终余额一致。

## 9. SYS-03 配置与版本系统

### 9.1 系统目标

使作物、配方、建筑、订单、等级和任务能够数据驱动。

### 9.2 配置表

| 表名 | 用途 |
|---|---|
| `ItemConfig` | 物品基本定义 |
| `CropConfig` | 作物和种植参数 |
| `BuildingConfig` | 建筑和建造成本 |
| `RecipeConfig` | 生产配方 |
| `LevelConfig` | 等级经验和奖励 |
| `UnlockConfig` | 内容解锁条件 |
| `OrderItemConfig` | 可进入订单的商品及权重 |
| `OrderTierConfig` | 订单档位和奖励倍率 |
| `QuestConfig` | 任务流程和奖励 |
| `ErrorTextConfig` | 用户可见错误文本 |
| `GuideConfig` | 引导步骤和 UI 指向 |

### 9.3 ID 规则

建议使用带类别号的整数 ID，数据库存整数，编辑器可显示文本别名：

```text
1xxxxx 货币
2xxxxx 作物
3xxxxx 加工品
4xxxxx 建筑
5xxxxx 配方
6xxxxx 任务
7xxxxx 订单模板或档位
```

示例：`20001 = 小麦`，`30001 = 面粉`，`40001 = 磨坊`。

### 9.4 配置发布规则

- 配置包含 `configVersion` 和 `minClientVersion`。
- 服务端启动时校验外键、重复 ID、负数和循环解锁。
- 客户端只读取表现和预览字段；服务端使用权威数值配置。
- 已运行中的生产保存 `recipeId`、开始时间和结束时间。V0.1 配置变更后不追溯修改已经开始的生产结果。
- 删除配置时必须先确认没有线上玩家实例引用。

### 9.5 验收标准

- 修改作物生长时间后重新发布配置即可生效。
- 非法配方引用不存在物品时，服务端拒绝加载配置。
- 客户端配置版本不兼容时不能进入主场景。

## 10. SYS-04 服务器时间与离线结算

### 10.1 核心规则

V0.1 不做“离线收益包”，只让已开始的计时继续流逝：

- 作物离线期间可以成熟。
- 生产任务离线期间可以完成。
- 完成的产品不会自动进入背包，玩家上线后主动收取。
- 生产队列按顺序自动继续，但只有开工时已扣除材料的任务才会执行。
- 订单不会因离线自动完成。

### 10.2 客户端时间差

```text
serverOffset = serverTime - clientRealtime
estimatedServerTime = clientRealtime + serverOffset
```

客户端每次收到业务响应时平滑校正 `serverOffset`。如果偏差超过 3 秒，立即修正倒计时。

### 10.3 离线摘要

登录后如有变化，显示：

- 成熟作物数量
- 完成生产数量
- 新解锁内容数量

摘要只用于提示，不发额外奖励。

### 10.4 异常规则

- 修改手机时间不影响结果。
- 倒计时显示为 0，但服务端尚未完成时，客户端刷新服务器时间并短暂显示“正在完成”。
- 服务端时间回拨属于严重运维异常，应报警，不在业务层容忍。

## 11. SYS-05 物品、货币与背包系统

### 11.1 物品分类

| 类型 | 是否占仓库 | 是否可主动出售 | V0.1 用途 |
|---|---:|---:|---|
| Currency | 否 | 否 | 铜钱、玉石 |
| Crop | 是 | 是 | 农作物 |
| Material | 是 | 是 | 基础材料，首版较少 |
| Product | 是 | 是 | 加工产品 |
| Quest | 否 | 否 | 预留，首版尽量不用 |
| Decor | 否 | 否 | 后续版本预留 |
| Consumable | 是 | 否 | 后续加速道具预留 |

### 11.2 背包规则

- V0.1 使用总容量制，不限制单格堆叠上限。
- 每 1 个 Crop、Material、Product 占 1 容量。
- 初始容量 100，首版不可扩容。
- 货币、任务物品和未来装饰不占容量。
- 收获和领取生产物前必须校验容量。
- 任务、邮件等不可丢失奖励在背包满时不直接领取，并提示先清理仓库。
- 本版本不做临时溢出仓。

### 11.3 主动出售

为了防止满仓死锁，背包允许按系统价格出售作物和加工品：

- 选择物品和数量。
- 服务端校验物品数量。
- 扣除物品并增加铜钱。
- 出售价格取 `ItemConfig.sellPrice`。
- 不允许一键出售全部，至少保留二次确认。

订单奖励应高于直接出售约 25%～60%，鼓励经营而非直接清仓。

### 11.4 通用资源变化结构

```text
- resourceType
- resourceId
- delta
- before
- after
- reasonType
- reasonId
```

一次操作返回全部变化，用于客户端播放奖励动画。

| INVENTORY_NOT_ENOUGH | 物品不足 | 刷新背包并提示 |
| INVENTORY_FULL | 仓库空间不足 | 打开背包清理入口 |

| `GET /resource/logs` | 开发环境查询资源流水 |

### 11.7 验收标准

- 背包 99/100 时不能领取 2 个物品。
- 重复出售请求只执行一次。
- 所有物品来源和消耗均有业务原因记录。

## 14. SYS-08 加工生产系统

### 14.1 系统目标

将基础作物转化为高价值商品，为订单系统提供规划空间。

### 14.2 队列规则

- 每座建筑默认 2 个队列格。
- 玩家可以预先加入 2 个任务。
- 加入队列时立即扣除全部材料。
- 第一个任务立即开始。
- 当前任务完成后，下一个任务自动开始。
- 完成的任务占用原队列格，必须收取后才空出位置。
- 如果第一个完成但未收取，第二个仍按预定顺序继续计时。
- V0.1 不支持取消生产，避免材料返还和队列重排复杂度。

### 14.3 生产任务状态

```text
Queued：已扣材料，等待前序任务
Producing：生产中
Completed：已完成，等待收取
Claimed：已收取，从有效队列移除
```

```text
- buildingInstanceId
- queueIndex
- recipeId
- state
- startTime
- finishTime
- outputItemId
- outputCount
- createTime
- revision
```

加入队列时服务端根据已有队列计算开始时间：

```text
startTime = max(serverNow, 前一个任务 finishTime)
finishTime = startTime + recipeDuration
```

## 15. SYS-09 订单系统

### 15.1 系统目标

持续消耗玩家物品，并为玩家提供铜钱和经验，是 V0.1 的主要成长驱动。

### 15.2 解锁和槽位

- 完成任务 T008 后解锁订单板。
- 同时展示 4 张订单。
- 提交订单后，2 秒后生成新订单。
- 玩家每 30 分钟有一次免费主动刷新机会。
- V0.1 不做付费刷新。
- 剧情首单由固定模板生成，之后使用权重随机。

### 15.3 订单数据

```text
OrderInstance
- orderId
- slotIndex
- tier
- requirements[]
- rewardCoin
- rewardExp
- createTime
- expireTime
- state
- seed
- revision
```

V0.1 普通订单不设过期时间，`expireTime` 预留。

### 15.4 生成规则

1. 只选择玩家已经解锁的物品。
2. 只有玩家已经建造对应建筑时，加工品才能进入订单池。
3. 单张订单包含 1～2 种物品。
4. 1～3 级订单只要求 1 种物品。
5. 不连续生成 3 张包含同一种高耗时商品的订单。
6. 至少保留 1 张主要由基础作物组成的低难度订单。
7. 订单总预计生产时间不能超过当前档位上限。
8. 不直接读取玩家库存来保证“必定可交”，但可降低当前严重缺货商品的权重。
9. 刷新订单不能得到低于原订单档位的奖励价值。

### 15.5 订单档位

| 档位 | 解锁等级 | 物品种类 | 预计耗时 | 奖励倍率 |
|---|---:|---:|---:|---:|
| 普通 | 1 | 1 | 1～8 分钟 | 1.25 |
| 丰盛 | 4 | 1～2 | 8～25 分钟 | 1.40 |
| 珍贵 | 7 | 1～2 | 25～60 分钟 | 1.60 |

### 15.6 奖励计算

每个物品配置 `baseValue`。订单基础价值为全部要求物品价值之和：

```text
rewardCoin = round(sum(baseValue × count) × tierMultiplier)
rewardExp = round(sum(itemExpValue × count) × expMultiplier)
```

最终结果生成时写入订单实例，后续配置变化不追溯修改现有订单。

### 15.7 提交流程

```text
点击提交
→ 客户端展示将消耗的物品和奖励
→ 服务端校验订单状态
→ 校验全部物品数量
→ 扣除物品
→ 增加铜钱和经验
→ 标记订单完成
→ 处理升级和新解锁
→ 创建替代订单
→ 触发 ORDER_COMPLETE 任务事件
→ 返回所有资源、等级、解锁和订单变化
```

### 15.8 刷新规则

- 免费刷新冷却按订单板整体计算。
- 玩家指定刷新某一个槽位。
- 刷新不会返还或消耗物品。
- 新订单不得与被刷新订单完全相同。
- 首张教学订单不能刷新。

### 15.9 主要接口

| 接口 | 用途 |
|---|---|
| `POST /order/submit` | 提交订单 |
| `POST /order/refresh` | 刷新指定槽位 |
| `GET /order/list` | 获取订单列表和刷新冷却 |

### 15.10 异常与边界

- 物品不足：返回每项拥有数和需要数。
- 订单已提交：重复请求按幂等结果返回。
- 玩家等级在交付时提升：同一事务中完成升级并返回解锁列表。
- 新订单生成失败：订单槽暂时为空并记录严重错误；玩家资源结算不能因此回滚丢失。
- 服务端可通过修复任务补充空订单槽。

### 15.11 验收标准

- 订单不会要求未解锁物品。
- 至少一个槽位保持低难度订单。
- 提交时物品、金币和经验变化正确。
- 连续提交和弱网重试不能重复发奖。

| T014 | 山居渐盛 | 达到 5 级 | 20 玉石 |
| T015 | 第一阶段完成 | 累计完成 12 张订单 | 300 铜钱、阶段完成标记 |

任务奖励需要根据实际测试调整，任何强制建造任务都必须提供足够资源或防卡死机制。

### 17.6 引导表现

引导分为两类：

1. 强引导：遮罩其他区域，只允许点击指定控件。仅用于前 5 分钟关键步骤。
2. 弱引导：箭头、气泡、任务跳转。完成第一张订单后主要使用弱引导。

强引导必须支持：

- 断线恢复
- 重进场景恢复
- 目标控件不存在时自动降级为文字提示
- 开发环境跳过

### 17.7 任务防卡死

- 不要求玩家上交唯一物品。
- 建造任务奖励必须覆盖关键费用。
- 如果玩家提前完成某条件，任务激活时应进行一次当前状态回溯检查。
- “拥有物品”检查当前库存；“获得物品”统计激活后的增量，两者配置类型必须区分。
- 删除或修改任务配置时保留已完成玩家状态兼容。

### 17.8 主要接口

| 接口 | 用途 |
|---|---|
| `GET /quest/list` | 获取任务列表 |
| `POST /quest/claim` | 领取任务奖励 |
| `POST /guide/progress` | 保存客户端引导步骤 |

### 17.9 验收标准

- 玩家可以从 T001 连续完成到 T015。
- 中途退出后回到正确引导步骤。
- 提前拥有任务物品不会导致任务无法完成。
- 重复领取任务奖励不会重复发放。

V0.1 只做必要红点：

- 有可领取任务奖励
- 有可收取生产产品
- 有可提交订单
- 有未读邮件

红点只表示可立即执行的收益操作，不对“可以播种”等常态行为持续提示。

### 18.5 网络交互规则

- 玩家点击后立即显示轻量等待状态，防止重复操作。
- 超过 500ms 可以显示局部加载图标。
- 超过 5 秒提示网络较慢并允许重试。
- 写请求超时不能直接判定失败；使用原 `requestId` 查询或重试。
- 成功响应到达前不提前播放确定性奖励动画。
- 状态冲突时重新获取对应系统状态，不必总是重登。

### 18.6 验收标准

- 主要功能在 3 次点击内可到达。
- 任务跳转能定位农田、建筑和订单板。
- UI 快速开关不产生重复请求和空引用。
- 常见屏幕比例下关键按钮不被遮挡。

## 22. API 返回约定

### 22.1 通用响应

```json
{
  "code": 0,
  "message": "OK",
  "serverTime": 0,
  "requestId": "...",
  "revision": 12,
  "data": {},
  "changes": []
}
```

### 22.2 错误分类

| 分类 | 处理方式 |
|---|---|
| 参数错误 | 提示并记录客户端错误 |
| 状态冲突 | 拉取对应模块最新状态 |
| 资源不足 | 显示缺少内容 |
| 未解锁 | 显示解锁条件 |
| 认证失败 | 刷新 Token 或重新登录 |
| 配置不一致 | 返回启动流程更新配置 |
| 服务异常 | 保留 requestId，允许重试 |

### 22.3 不建议的做法

- 每次操作后返回整个玩家存档。
- 客户端自己扣资源再等待服务端同步。
- 用字符串作为所有配置主键。
- 为每块农田启动一个常驻服务端定时器。
- 用客户端上传的完成时间判断生产结果。
- 把任务完成逻辑散落在 Unity 各个 UI 脚本中。

## 26. 测试清单

### 26.1 正常流程

- 新账号完整完成 15 个任务。
- 6 种作物均可种植和收获。
- 9 个配方均可生产和领取。
- 3 种订单档位均能生成。
- 玩家能正常升至 10 级。

### 26.2 时间与离线

- 播种后立即退出，成熟后重新登录。
- 生产队列有两个任务时退出，两个任务均按顺序完成。
- 修改客户端系统时间后尝试提前收获。
- 客户端倒计时与服务端相差时能够纠正。

### 26.3 重复与并发

- 连续点击两次播种。
- 连续点击两次收获。
- 相同 requestId 重复提交订单。
- 两台设备同时操作同一农田。
- 提交订单时另一请求先出售了所需物品。
- 领取任务奖励时客户端断线后重试。

### 26.4 容量和资源不足

- 背包正好剩余一个容量时收获两个物品。
- 背包满时领取生产产品。
- 金币不足时建造建筑。
- 材料不足时开始生产。
- 订单需要的物品部分不足。

### 26.5 配置和版本

- 客户端和服务端配置版本不一致。
- 配方引用不存在物品。
- 作物已经播种后修改生长时间。
- 生产开始后修改配方产量。
- 玩家存档引用已经下线的配置 ID。

### 26.6 恢复能力

- 写数据库成功但响应客户端前断线。
- 服务端处理订单时进程退出。
- 新玩家创建过程中重复请求。
- 某个订单槽数据缺失时自动修复。
- 邮件附件领取后客户端未收到响应。

## 28. 本版本最大的三个风险

### 风险一：数值循环卡死

玩家可能把金币花完，导致没有钱播种或建造。处理方式：

- 初始金币留足缓冲。
- 关键建造任务补足费用。
- 保留基础作物低成本种植。
- 必要时提供每日一次最低生活补助，但 V0.1 先不默认开启。

### 风险二：服务端业务状态不一致

订单同时涉及背包、货币、经验、任务和新订单，容易出现部分成功。处理方式：

- 使用数据库事务。
- 统一资源服务。
- requestId 幂等。
- 返回完整变化集合。
- 资源流水支持追查。

### 风险三：首版范围失控

自由摆放、多角色剧情和实时多人都会显著扩大开发量。处理方式：

- V0.1 建筑固定点位。
- 任务只使用文字和简单气泡。
- 不实现好友与大厅。
- 任何新增需求先判断是否直接服务核心经营闭环。
